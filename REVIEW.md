# Design Review — Meu Patrimônio

## Executive assessment

The application has a solid functional foundation and a coherent dark visual language, but currently feels more like a capable personal utility than a premium wealth product.

Its strongest qualities are its focused scope, clear Brazilian Portuguese, sensible empty states, contribution-adjusted performance calculations, local-first storage with Firebase synchronization, and cautious import and backup workflows. The largest design gap is not decoration: it is the absence of a strong financial story that immediately explains where the user stands, what changed, and what deserves attention.

### Overall assessment

| Dimension | Assessment |
|---|---:|
| Overall design maturity | 6/10 |
| Functional trust | 7.5/10 |
| Perceived premium quality | 5/10 |

The review was conducted in read-only mode. No application files, Firebase configuration, or stored user data were modified.

## Review scope and limitations

The requested Impeccable skill was not exposed in the available skill catalog, and no readable local copy was found. The connected visual browser was also unavailable. Visual conclusions are therefore based on the complete interface source, screen structure, responsive rules, interaction states, chart implementation, and accessibility semantics rather than a rendered-device walkthrough.

## Product positioning

The product’s strongest potential position is:

> A calm, private, user-controlled monthly wealth tracker that separates contributions from investment performance.

This is more distinctive than trying to become a trading terminal or a full-service bank. The redesign should preserve the product’s simplicity and monthly-closing model while improving comprehension, confidence, and perceived quality.

## What is already working well

- The product has a clear core model: monthly closings, investments, contributions, evolution, and projections.
- Contribution-adjusted performance is a meaningful differentiator.
- The interface explains that deposits are excluded from return calculations.
- Local persistence combined with Firebase synchronization communicates resilience.
- Import, export, backup, and merge behavior are unusually thoughtful for a focused personal tool.
- Empty states generally tell the user what to do next.
- The review-before-save workflow reduces errors generated by OCR.
- The dark palette is restrained and appropriate for a wealth product.
- Currency formatting, monthly organization, and terminology feel native to Brazilian users.
- Projection assumptions are disclosed instead of being presented as certainty.
- Major calls to action generally have reasonable tap targets.
- Destructive actions require confirmation.
- Images used during OCR are not retained in the historical data.

## Overall UX

### Strengths

The main workflow is understandable:

1. Create investments.
2. Select a month.
3. Add values manually or from screenshots.
4. Review recognized data.
5. Save the monthly closing.
6. Inspect the portfolio, evolution, or projections.

The review stage is especially valuable because it makes OCR an assistive mechanism rather than an invisible source of truth.

### Issues

The experience is organized around product features rather than the user’s financial questions. The home screen shows a balance and a performance delta, but does not form a complete story:

- What changed this month?
- How much of the change came from contributions?
- How much came from return?
- Which investments drove the result?
- How is the portfolio allocated?
- Is anything incomplete or out of sync?

The monthly-closing workflow is also represented in multiple places: a bottom-navigation item, a header plus button, and a home call to action. This makes a core action feel less intentional.

Native browser confirmation dialogs protect data but interrupt the visual system and diminish perceived quality. Destructive and consequential actions should use consistent in-app confirmation patterns with clearer context.

## Information architecture

The current bottom navigation contains:

1. Fechamento
2. Configurações
3. Carteira
4. Evolução
5. Projeções

This mixes an action, “Fechamento,” with destination-level sections. Settings receives unusually prominent placement despite being a low-frequency destination. Carteira is conceptually the home screen but appears third in reading order.

### Recommended navigation model

- Carteira
- Evolução
- Projeções
- Ajustes

“Novo fechamento” should become one distinct primary action, either within the home screen or as a central action treatment. It should not simultaneously behave as a navigation destination and appear in multiple other locations.

Settings should be reorganized internally into clearer groups:

- Conta e sincronização
- Investimentos
- Importação e exportação
- Backup e recuperação

Administrative functionality should remain available without competing with everyday portfolio tasks.

## Visual hierarchy

The visual hierarchy is too flat. Nearly every content group is presented as a dark rounded card with a subtle border. As a result, portfolio balance, projections, account synchronization, backup controls, forms, and explanatory content often receive similar emphasis.

The interface needs three clearer levels:

1. Primary financial information
2. Supporting analysis
3. Utility and administrative controls

The portfolio total should dominate the home screen. Performance, contributions, and allocation should form the next layer. Import, backup, and synchronization controls should visually recede until needed.

## Typography

The total balance receives strong scale and weight, which is appropriate. The remainder of the system relies too heavily on very small type and high font weights.

Supporting text frequently falls between approximately `0.61rem` and `0.75rem`. Navigation labels become as small as `0.51rem` on narrow screens. These sizes weaken legibility and perceived confidence, particularly for:

- Dates
- Performance assumptions
- Contribution metadata
- Projection results
- Synchronization information
- Explanatory financial copy

### Recommended typography principles

- Essential secondary data: 13–14 px
- Body and explanatory copy: 15–16 px
- Navigation labels: at least 11–12 px
- Financial totals: tabular numerals
- Stronger differentiation through size and spacing, not only font weight
- Fewer uses of 800–900 weights
- More generous line height for explanations
- Consistent roles for eyebrow, title, section heading, body, label, metadata, and numeric value

Currency should have a deliberate hierarchy. The integer portion may carry more visual weight than cents, but the representation must remain accessible and unambiguous.

## Spacing

The interface has consistent local spacing, but the system does not establish sufficiently different rhythms for:

- Page-level sections
- Card interiors
- Form groups
- Related values
- Unrelated administrative groups

The result is visually dense despite generous rounded containers.

### Recommended spacing system

Use an 8 px base scale, with a limited set such as:

- 4 px for tightly related metadata
- 8 px for compact internal gaps
- 12 px for controls and list content
- 16 px for standard card padding
- 24 px between page sections
- 32 px before major analytical sections

Whitespace should communicate grouping before borders and background fills are added.

## Color palette

The dark blue-green palette is appropriate, restrained, and more sophisticated than a generic black financial interface. The mint green accent communicates growth and confidence.

However, green is used both as a semantic performance color and as the default accent for many actions. This reduces its meaning. Premium financial products generally distinguish:

- Brand or interactive accent
- Positive performance
- Negative performance
- Warning
- Informational state
- Neutral selection

The muted text color may be too subtle when combined with very small type. Contrast should be verified for all secondary text, disabled controls, chart labels, and status colors.

Recommended direction:

- Preserve the dark blue-green foundation.
- Reserve performance green primarily for positive financial values.
- Use a distinct but compatible action accent or a neutral high-contrast button treatment.
- Keep red restrained and contextual.
- Avoid relying on yellow alone for contribution or warning meaning.
- Define colors as semantic tokens rather than component-specific values.

## Cards

The card system is internally consistent but overused. Rounded cards currently contain almost every kind of content, producing “card fatigue.”

Premium products tend to reserve elevated or strongly bounded surfaces for coherent summaries and decisions. Lists and supporting values can often sit directly on the page with separators.

### Recommendations

- Keep one prominent portfolio summary surface.
- Present investments as a structured list rather than a collection of card-like buttons.
- Reserve inset cards for scenarios, warnings, grouped controls, and focused decisions.
- Remove borders where surface contrast already creates sufficient separation.
- Standardize radii instead of using many values between approximately 10 and 24 px.
- Use elevation sparingly and consistently.
- Avoid nested cards unless the hierarchy truly requires them.

## Financial dashboard

The home dashboard currently emphasizes total wealth and a single delta. It needs to become a decision-support summary without turning into a trading terminal.

### Recommended dashboard content

1. Total portfolio
2. Return for the selected period
3. Contributions for the selected period
4. Net change in wealth
5. Last closing and synchronization status
6. Allocation by investment
7. Top positive and negative performance contributors
8. Progress toward the selected goal

The distinction between net wealth change and investment return must be explicit. This is already supported conceptually by the application’s contribution-adjusted calculations and should become a central visual advantage.

The dashboard should also identify meaningful action states:

- Current month has no closing
- Contributions are pending
- Data is syncing
- Device is offline
- A closing needs review

## Charts

The current evolution visualization is a fixed-height canvas line chart. It has a clean visual base but is presentational rather than analytical.

### Current limitations

- No accessible textual or tabular equivalent
- No touch inspection or tooltip
- No selected-point state
- No time-range control
- No contribution overlay
- No switch between wealth and return
- No benchmark comparison
- Every monthly label is rendered, which will become crowded
- Fixed height does not adapt meaningfully to landscape or very small screens

### Recommended chart behavior

- Time filters: 3M, 6M, 1A, and Tudo
- Touch and keyboard inspection for every point
- Selected-point summary containing:
  - Month
  - Closing balance
  - Contributions
  - Absolute return
  - Percentage return
- Toggle between:
  - Patrimônio
  - Rendimento
  - Aportes
- Dynamic axis-label density
- Visual separation between organic performance and deposits
- Accessible table or summary beneath the chart

The relevant lesson from TradingView is inspectability, not complexity. The product does not need indicators, drawing tools, or professional trading controls.

## Projections

The existing projection section is useful and responsibly states that its estimates assume constant monthly returns and no future contributions.

The three fixed scenarios, however, are compressed into narrow columns on mobile and display precise dates. This can imply more certainty than the underlying assumptions support.

### Recommendations

- Stack scenario cards vertically on small screens.
- Make the target amount adjustable.
- Allow an expected monthly contribution.
- Present conservative, base, and optimistic assumptions.
- Display an estimated range where appropriate.
- Explain whether values are nominal.
- Keep assumptions adjacent to results rather than only in a footer.
- Show how the estimate changed since the previous closing.
- Preserve the current disclaimer.

## Navigation

The fixed bottom navigation is appropriate for mobile and already accounts for the safe-area inset.

Its primary problems are:

- Five items force very small labels.
- The order does not reflect frequency or conceptual hierarchy.
- An action is mixed with destinations.
- Icons are text glyphs rather than a consistent icon system.
- The active item is communicated visually but not with `aria-current`.
- Settings is too prominent.

Reducing the navigation to four destinations will improve readability, tap confidence, and perceived polish.

## Interactions

### Positive interaction patterns

- Monthly saves require confirmation.
- Duplicate months are handled explicitly.
- Destructive actions require confirmation.
- OCR output is reviewed before persistence.
- Import and merge workflows explain their consequences.
- Cloud and file statuses provide feedback.
- Several sheets close when the backdrop is selected.

### Issues

- Native `confirm()` dialogs break visual continuity.
- Bottom sheets lack semantic dialog roles.
- Focus is not trapped within open sheets.
- Focus is not restored to the invoking control.
- Escape-key dismissal is absent.
- Some icon-only controls measure only 30–36 px.
- The header plus button has no accessible label.
- Editing and deletion are placed together as small actions.
- Loading, disabled, success, and error states are not consistently designed across controls.
- Toasts are not clearly exposed to assistive technology.
- Immediate scale-on-press behavior exists, but motion is not governed by a system.

### Recommended interaction principles

- Consequential actions should explain the object, date, amount, and outcome.
- Destructive actions should be visually separated from frequent actions.
- Sheets should support backdrop click, Escape, focus trapping, and focus restoration.
- Every async action should define idle, loading, success, error, and disabled states.
- Motion should confirm state changes, not decorate them.

## Accessibility

### Existing strengths

- The page language is Brazilian Portuguese.
- Most form inputs have visible labels.
- Fields and category controls have visible focus treatments.
- Several status messages use `aria-live`.
- Some icon-only close and delete controls have accessible names.
- Financial category buttons receive descriptive generated labels.

### Material gaps

- The canvas chart has no accessible equivalent.
- Bottom sheets are not semantic dialogs.
- Focus is not managed when overlays open or close.
- Active navigation state is visual only.
- Several glyph icons may be announced ambiguously.
- Major icon-only buttons lack accessible names.
- Multiple controls fall below a comfortable 44×44 px target.
- Very small muted text reduces practical readability.
- Color carries substantial meaning.
- There is no `prefers-reduced-motion` handling.
- Toast messages are not clearly live regions.
- Dynamic view changes do not move or announce focus.
- Dynamic headings and view titles may not provide sufficient screen-reader context.

Accessibility should be treated as a structural design pass, not a final compliance check.

## Mobile experience

The application has a strong mobile foundation:

- A focused maximum content width
- Safe-area-aware bottom navigation
- Responsive form layouts
- Full-width primary actions
- Bottom-sheet patterns
- Sensible collapsing of multi-column fields

### Mobile issues

- Five navigation labels become too small.
- Projection cards are excessively compressed.
- Sticky review summary may compete with the fixed navigation.
- Dense contribution and investment metadata becomes difficult to scan.
- Settings becomes a long, undifferentiated sequence.
- Sheet content does not explicitly account for keyboard height and overflow.
- The fixed chart height is not ideal in landscape.
- Narrow-screen typography becomes smaller precisely when readability is most constrained.

The redesign should prioritize common phone widths before optimizing the 560 px maximum layout.

## Perceived quality

The application feels coherent and trustworthy at a functional level, but several details prevent a premium impression:

- Generic text glyphs instead of a deliberate icon system
- Excessive use of rounded cards
- Very small typography
- Native browser confirmations
- Limited chart interaction
- Visually equal treatment of primary finance content and utilities
- Repeated accent treatments
- Sparse loading and transition states
- No distinctive brand signature

Premium quality should come from disciplined hierarchy, precise type, confident spacing, responsive feedback, and transparent financial logic. It should not depend on decorative gradients or animation volume.

## Benchmark comparison

| Product | Relevant strength | Current opportunity |
|---|---|---|
| Apple Stocks | Ruthless hierarchy, strong numerical typography, effortless scanning | Reduce equivalent surfaces and make financial movement easier to inspect |
| Revolut | Progressive disclosure, polished states, contextual analytics | Separate primary wealth insights from administrative utilities |
| TradingView | Inspectable time-series data and strong chart interaction | Add point-level inspection without importing professional-trading complexity |
| Kinvo | Allocation, portfolio performance, and benchmark context | Add allocation visualization and clearer performance attribution |
| BTG Pactual | Institutional trust and structured performance reporting | Strengthen authority, hierarchy, and reporting clarity |

The recommended combination is:

> The calmness of Apple Stocks, the polish of Revolut, the portfolio clarity of Kinvo, and only the necessary chart intelligence from TradingView.

The app should not imitate the density of a brokerage platform. Its advantage is a quieter, personally controlled monthly view of wealth.

## Recommended north-star home screen

The ideal home screen should communicate this sequence:

1. **What I have:** total portfolio
2. **What changed:** net change and return
3. **Why it changed:** contributions versus performance
4. **Where it is:** allocation by investment
5. **What needs action:** missing closing, pending contribution, or sync issue
6. **Where I am going:** compact progress toward the selected goal

This structure would move the product closest to premium personal-finance quality while preserving its strongest differentiator: simple, user-controlled monthly wealth tracking.

## Prioritized implementation roadmap

### Pass 1 — Clarity, accessibility, and navigation

**Objective**

Make the existing product easier to understand and operate without changing its calculations, Firebase integration, persistence model, or stored data.

**Expected visual impact**

High. The interface will immediately feel calmer, more legible, and more intentional through clearer navigation, stronger type, better control sizing, and consistent interaction states.

**Planned work**

- Reorganize bottom navigation into Carteira, Evolução, Projeções, and Ajustes.
- Consolidate new-closing entry points into one primary action.
- Establish a practical type scale and remove critically small text.
- Replace ambiguous glyphs with a consistent accessible icon system.
- Add accessible names and `aria-current`.
- Add dialog semantics, focus trapping, focus restoration, and Escape dismissal.
- Bring interactive targets to at least 44×44 px where practical.
- Add reduced-motion behavior.
- Improve visible focus across all interactive elements.
- Replace native confirmations with consistent in-app confirmation sheets.
- Add an accessible chart summary.
- Clarify “aporte,” “rendimento,” and “variação do patrimônio.”

**Files likely to change**

- `index.html`
- A future stylesheet if CSS is extracted from `index.html`
- A future interaction script if JavaScript is extracted from `index.html`
- Optional icon assets or an icon component source

**Implementation risk**

Low. Most work affects presentation, semantics, and navigation wiring. The primary risk is breaking current view switching or focus behavior. Firebase calls, IndexedDB records, import formats, and financial calculations should remain untouched.

### Pass 2 — Portfolio dashboard and visual system

**Objective**

Turn the home screen from a balance display into a concise portfolio story using metrics already available in the application.

**Expected visual impact**

Very high. This pass creates the largest improvement in perceived product value by making portfolio status, contributions, returns, and allocation understandable at a glance.

**Planned work**

- Redesign the home summary around total portfolio, return, contributions, net change, and last update.
- Add a compact allocation visualization derived from existing category totals.
- Show the strongest positive and negative contributors to monthly performance.
- Replace repeated card treatments with a clearer surface hierarchy.
- Standardize spacing, radii, color roles, borders, and typography as reusable tokens.
- Introduce tabular numerals.
- Reserve green primarily for positive financial performance.
- Separate portfolio content from synchronization and administrative state.
- Redesign empty states as guided sequences.
- Simplify investment rows and improve comparative scanning.

**Files likely to change**

- `index.html`
- A future design-token or stylesheet file if styles are extracted
- A future dashboard-rendering script if JavaScript is extracted
- No Firebase schema or stored-data migration should be required

**Implementation risk**

Low to moderate. Most dashboard metrics can be derived from existing closings, contributions, and categories. Risk comes from ensuring that every displayed metric uses the same contribution-adjusted logic as the current performance calculations.

### Pass 3 — Evolution, attribution, and projections

**Objective**

Make financial analytics explain change instead of only plotting balances, while keeping the experience appropriate for a personal wealth tracker.

**Expected visual impact**

High. Evolution and projection screens will feel substantially more capable and comparable to premium portfolio products.

**Planned work**

- Add 3M, 6M, 1A, and Tudo time filters.
- Make chart points inspectable by touch, pointer, and keyboard.
- Add selected-point details for balance, contributions, absolute return, and percentage return.
- Add Patrimônio, Rendimento, and Aportes modes.
- Visually distinguish deposits from organic performance.
- Adjust axis-label density dynamically.
- Add monthly and accumulated return summaries.
- Expose contribution-adjusted attribution by investment.
- Stack projection scenarios on mobile.
- Allow users to adjust the target amount and expected monthly contribution.
- Present conservative, base, and optimistic scenarios.
- Prefer ranges over false date precision where appropriate.
- Keep external benchmarks out of scope unless a reliable data source is intentionally introduced.

**Files likely to change**

- `index.html`
- Chart rendering and interaction logic, currently embedded in `index.html`
- Projection calculation and rendering logic, currently embedded in `index.html`
- A future chart component or module if the monolithic file is later separated
- Possibly tests for financial calculations if a test structure is introduced

**Implementation risk**

Moderate. Chart interaction, responsive behavior, and scenario calculations add state and edge cases. Any new inputs must remain local or use an explicitly designed storage extension. Existing closings and Firebase documents should not be mutated or reinterpreted.

### Pass 4 — Premium polish and confidence

**Objective**

Refine feedback, motion, edge cases, and brand expression after the structural and analytical improvements are stable.

**Expected visual impact**

Moderate to high. This pass will not change the core information architecture, but it will materially improve perceived craftsmanship, responsiveness, and trust.

**Planned work**

- Refine motion for sheets, chart transitions, save confirmation, and synchronization.
- Add skeleton and contextual loading states.
- Design offline, syncing, synced, conflict, and error states.
- Improve microcopy for OCR confidence, merge behavior, backup, and irreversible actions.
- Add restrained haptic feedback where supported.
- Introduce a subtle and consistent brand signature.
- Test compact phones, large phones, landscape, browser zoom, dynamic text, keyboard navigation, and screen readers.
- Validate contrast.
- Test long investment names, large values, negative performance, missing months, and long histories.
- Run task-based usability testing around monthly closing, correction, import, and recovery.

**Files likely to change**

- `index.html`
- A future stylesheet and interaction module if the file is separated
- Optional brand and icon assets
- Optional manifest or platform metadata if the product later adopts installable-app behavior
- Test and accessibility audit files if introduced

**Implementation risk**

Moderate. Individual polish changes are low risk, but their breadth can create inconsistent states if introduced without a settled component system. Motion, loading behavior, and offline messaging must not interfere with Firebase synchronization or imply that data is saved before persistence succeeds.
